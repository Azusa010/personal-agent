## 1. 整体方案

PersonalAgent 采用「协议层集中定义错误码 + 两端按约定返回结构化结果」的混合模式：
- TS（Electron Main）侧对能力执行使用 `{ ok, code?, reason? }` 的结果对象，通过 `fail(code, reason)` 构造失败分支；成功时返回 `{ ok: true, ... }`。
- Python（agent-runtime）侧在 JSON-RPC 请求/响应层用 Pydantic 模型校验参数，异常被捕获后转为 `build_error(req_id, code, message)` 形式的标准 JSON-RPC error 对象。
- 两层之间通过 `HostExecuteToolResult` / `Observation.ok` 桥接：TS 返回 `{ok, code, reason}`，Python 引擎将其包装为 `Observation(ok=result.ok, payload=dict(result.model_extra or {}))`，再透传给上层事件流。

该设计把「协议级错误」（JSON-RPC 层）和「能力级错误」（工具调用结果）解耦：前者走 `error.code/message/data`，后者走 `ok+code+reason` 的轻量结构体。两者都避免抛未捕获异常，保证进程不会崩溃。

## 2. 关键文件与包

- `packages/protocol/schemas/errors.ts`：集中声明所有协议级错误码常量（`ERROR_CODE.*`），如 `PROTOCOL_INVALID_JSON`、`METHOD_NOT_FOUND`、`CAPABILITY_OUT_OF_SCOPE`、`PERMISSION_DENIED`、`PDF_EXTRACTION_FAILED` 等，作为 TS 侧唯一权威来源。随 WRITE 能力与调度器落地新增七个码：文件系统写操作类 `CREATE_DIR_FAILED`、`MOVE_SOURCE_MISSING`、`MOVE_TARGET_EXISTS`、`MOVE_FAILED`，调度类 `REMINDER_TIME_IN_PAST`、`REMINDER_ALREADY_EXISTS`、`SCHEDULER_CREATE_FAILED`。
- `apps/desktop/src/main/runtime/error-code.ts`：声明运行时内部错误码（`RUNTIME_ERROR_CODE.*`），如 `RUNTIME_TIMEOUT`、`RUNTIME_CRASHED`、`PLAN_NOT_BUILDABLE`、`DB_FAILED` 等，用于 Main 进程内部状态机错误。
- `packages/protocol/schemas/envelope.ts`：用 Zod 定义 JSON-RPC 2.0 的 Request/Response/Notification，并通过 `superRefine` 强制 `result` 与 `error` 互斥，防止同时存在或同时缺失。
- `packages/protocol/schemas/host.ts`：定义 host→main 的工具调用协议，包括 `CapabilityId` 枚举、`HostExecuteToolRequest/Response` 以及 `CapabilityFailure = { ok: false, code, reason }` 结构。
- `apps/desktop/src/main/capabilities/executor.ts`：能力执行器，将策略判定失败与 I/O 异常统一收敛到 `fail(ERROR_CODE.X, reason)`，是 TS 侧错误码的主要产出点；`runSchedulerCreate` 产出 `REMINDER_ALREADY_EXISTS`（异参重建被拒）与 `SCHEDULER_CREATE_FAILED`（落库失败，insert 与 reminder_created 事件同事务回滚），未接线 Reminder 存储时回 `NOT_IMPLEMENTED` 而不半创建状态。
- `apps/desktop/src/main/capabilities/filesystem-move.ts` / `filesystem-create-dir.ts`：写操作能力级错误码的产出点——move 有三个业务码（source 不存在 → `MOVE_SOURCE_MISSING`；target 已存在 → `MOVE_TARGET_EXISTS`，拒绝而非覆盖；rename 失败 → `MOVE_FAILED`），create_dir 的所有失败分支收敛到唯一出口 `CREATE_DIR_FAILED`。
- `apps/desktop/src/main/policy/argument-binders.ts`：scheduler.create 绑定器在参数绑定层以 `REMINDER_TIME_IN_PAST` 拒绝过去时间，连批准关都不进。
- `apps/desktop/src/main/capabilities/idempotency.ts`：幂等关（位于五层安全链的 Executor 环节内）reject 分支返回载荷码 `IDEMPOTENCY_CONFLICT`——该码不在 `ERROR_CODE` 注册表内，只出现在幂等关结果载荷中（见 3.5）。
- `services/agent-runtime/src/personal_agent/runtime.py`：Python 端 JSON-RPC 分发入口，`handle_line` → `dispatch` → 各 handler 均 catch `ValidationError` 并返回 `build_error(...)`；未知方法返回 `METHOD_NOT_FOUND`。
- `services/agent-runtime/src/personal_agent/engine.py`：Agent 循环，把所有失败路径汇聚到 `_fail(events, reason)`，生成 `RunTaskFailed(status="failed", reason, events)`；对预算耗尽、脚本耗尽、通道关闭等分别给出明确 reason。
- `apps/desktop/src/main/policy/task-context.ts`：定义 `TaskBusyError extends Error`，用于单槽并发保护；注释明确这是「编程错误」而非业务失败，直接拒而不排队。

## 3. 架构与约定

### 3.1 协议级错误（JSON-RPC 层）
- 所有 JSON-RPC 响应遵循 `envelope.ts` 的 Response schema：`result` 与 `error` 二选一，由 Zod 在反序列化时强制校验。
- Python 侧通过 `build_error(req_id, code, message)` 构造标准错误响应；TS 侧通过 `error.code/message/data` 字段接收。
- 已知错误码集中在 `errors.ts` 的 `ERROR_CODE` 常量中，新增错误必须在此注册，测试通过断言 `expect(out['code']).toBe(ERROR_CODE.X)` 验证。

### 3.2 能力级错误（工具调用结果）
- TS 能力执行器统一返回 `{ ok: boolean, code?: string, reason?: string }` 的 `CapabilityOutcome`。
- 成功：`{ ok: true, entries }` 等具体数据。
- 失败：`fail(code, reason)`，其中 `code` 来自 `ERROR_CODE`，`reason` 是面向人类的可读描述。
- Python 引擎收到后以 `Observation(ok, payload=code+reason)` 形式记录，并在最终 `RunTaskCompleted`/`RunTaskFailed` 事件中携带。

### 3.3 运行时内部错误
- `RUNTIME_ERROR_CODE` 专用于 Electron Main 进程内部状态机（超时、取消、崩溃、握手失败、计划无效、数据库失败、任务忙、孤儿任务等），不进入协议层。
- `TaskBusyError` 是唯一的自定义 `Error` 子类，用于单槽并发冲突；其他场景尽量用结果对象而非抛错。

### 3.4 异常捕获策略
- Python 侧：每个 handler 用 try/except 捕获 `ValidationError`（Pydantic）和通用 `Exception`，分别映射到 `PROTOCOL_INVALID_REQUEST` / `RUNTIME_INTERNAL` 等错误码，并记录日志。
- TS 侧：I/O 操作（如 `readFile`、`extractPdf`）用 try/catch 捕获后转成 `fail(ERROR_CODE.FILE_UNREADABLE | PDF_EXTRACTION_FAILED, describe(e))`；`describe(e)` 会提取 Node `ErrnoException.code` 以便调试。
- 测试中大量使用 `throw new Error(...)` 表达期望失败，但生产代码倾向返回结构化结果而非抛错。

### 3.5 幂等关结果载荷码（不在 ERROR_CODE 注册表）
- 幂等关 `beginAttempt`（Executor 环节内，只保护 WRITE_CAPABILITIES 中的 filesystem.move / filesystem.create_dir）在文件系统处于矛盾态时 reject，返回结果载荷 `{ ok:false, code:'IDEMPOTENCY_CONFLICT', reason }`。`IDEMPOTENCY_CONFLICT` 是 TS 侧字符串字面量，刻意不进 `ERROR_CODE` 注册表，Python 侧当作不透明字符串透传（与 RUNTIME_* 码同等待遇），测试断言也直接用字面量。
- skip 分支返回成功载荷：命中 succeeded 缓存时原样返回记录的 `resultPayload`；崩溃恢复按文件系统证据判 done 时翻 succeeded 并返回 `{ ok:true, idempotent:true }`。
- scheduler.create 走另一套幂等语义（不进 tool_executions 幂等关）：同参重试（同 `capability:argsHash` 幂等键）命中 reminders.task_id UNIQUE 记录时幂等返回已有记录且 `created:false`；异参再来拒绝 `REMINDER_ALREADY_EXISTS`，绝不静默用旧记录冒充成功。

## 4. 约定与约束

- **错误码集中管理**：协议级错误码只允许在 `packages/protocol/schemas/errors.ts` 中以 `as const` 对象声明，TS 侧通过 `ERROR_CODE.X` 引用，禁止硬编码字符串。
- **JSON-RPC 响应互斥**：`result` 与 `error` 不能同时出现也不能同时缺失，由 Zod `superRefine` 在反序列化阶段强制校验。
- **能力失败必须带 code+reason**：`CapabilityFailure` schema 要求 `ok=false` 时必须提供 `code` 与 `reason`，禁止空失败。
- **Python 运行时错误码独立命名空间**：`runtime.py` 中的 `RUNTIME_MODEL_NOT_CONFIGURED`、`PLAN_NOT_BUILDABLE` 等码属于 Python 单侧约定，注释明确「不进 packages/protocol 的 ERROR_CODE 注册表，TS 侧只把它当不透明字符串透传」。
- **单槽并发拒绝即编程错误**：`task-context.ts` 注释说明 `TaskBusyError` 不是业务失败而是编程错误，应直接拒绝而不是排队重试。
- **未知能力兜底**：`executor.ts` 的 switch default 分支返回 `NOT_IMPLEMENTED`，故意留作「加了 binder 忘了实现执行体」的安全网，而非抛出未捕获异常。
- **move 不做覆盖式幂等**：target 已存在直接拒（`MOVE_TARGET_EXISTS`）；重试/崩溃场景的幂等由 tool_executions 状态机（attempting/succeeded/failed，转换由 Repository 层 ALLOWED_TRANSITIONS 表约束）加文件系统证据判定保证，能力层绝不覆盖已有文件。
- **调度失败必须整体回滚**：`SCHEDULER_CREATE_FAILED` 场景下 Reminder insert 与 reminder_created 事件在同一事务内提交或回滚，不允许半创建状态；未接线存储时回 `NOT_IMPLEMENTED` 明说。
- **预算与步骤上限**：`engine.py` 的 `Budget` 限制最大步数与工具调用次数，超限时以 `EVENT_BUDGET_EXHAUSTED` 事件 + `RunTaskFailed` 返回，不抛异常。
- **日志与诊断分离**：Python 侧通过 `logging` 模块输出结构化日志到 stderr，错误信息通过 JSON-RPC error.message 返回给调用方，二者职责清晰。

## 5. 适用性判断

本仓库是一个包含 TypeScript (Electron) 与 Python 双端的 monorepo，错误处理贯穿协议层、能力执行层、运行时调度层，具有明确的集中式错误码定义、结构化的结果对象、严格的 JSON-RPC 响应校验以及跨语言的错误传播约定，因此该类别完全适用。
