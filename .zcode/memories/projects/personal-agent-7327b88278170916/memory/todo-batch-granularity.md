TASK-026（2026-09-15/16）我把陪练点一次铺成 9 个 `TODO(你填)` 加一份断言清单，主人的反应是先「不会写了」、再「写不下去了就这样吧」。同一轮里我给数据记录（`ToolCallEvidence`、`EvidenceBundle` 等）字段都加了 `readonly`，而给出的写法建议是「第二趟直接改那两个字段」——两句自相矛盾，等于把最直白的实现方式堵死。TASK-027（2026-09-16）改成只留一个（`judgeCase`）后，他自己填完了，我指出的三处 `selectedTarget` 问题与一处 reasons 计数他也自己改掉了——一次一个是对的路子。

**Why**：陪练的目标是让主人一格一格地推，不是铺满整本练习册；只要脚手架的类型约束挡住「构造/回填」这条路，卡点就从业务逻辑变成了我的摩擦。

**How to apply**：
1. 一次只推**一个**陪练点（一个函数 + 它自己的聚焦检查点用例），做完再给下一个；其余先用 fail-closed 占位（红点数量即进度）。
2. 数据记录类型（要留给人构造/回填的）字段一律可变：不加字段级 `readonly`，也不加只读数组。已写进 AGENTS.md §6。
3. 主人反馈卡住时，先把动作缩小到「一个函数、能编译、有一条命令能验证」，而不是补一轮更长的解释——长篇解释解决不了「不知道从哪下手」。
4. 收口时替主人补上留白的测试断言（TASK-027 那次是他说「可以了」之后补的 judge.test.ts 八条）——空转的用例（没有 expect）是恒绿的，留着比没有更糟。补之前先问一句还是直接补，看他当时的口气；补完要把「哪几条是我补的」说清楚。
5. **判定表类陪练点**（`judgeCase` / `judgeFault` 这种「给事实、出 ok+violations」的纯函数）要在类型注释里写死 `violations` 的语义，并给一个完整的 `case` 例子。TASK-028 的 `judgeFault` 他第一版就是把期望表当成违规列表推（无条件 `push('<期望的描述>')`），合规现场也恒判不通过——文档里写了期望表，没写「violations 装的是判不通过的理由，只有期望不成立才推」，这就是我留的坑。给这类点配的验收断言最好含一条「把现场改坏一点，判定必须翻脸」的 fail-closed 底线。
6. **契约要写到底层口径，别停在常见写法**：TASK-030 的 `buildRuntimeEnv` 契约只写了「空串不注入」，主人顺手写成 `if (settings.model)` 真值判断——`'  '` 这类纯空白被当成「设过了」注入环境（他自己写的 SCRIPT 分支就在用 `trim() !== ''`，口径不一致纯粹是我没写清）。这类边界要写成可判定的句子：存储层写盘前把纯空白归一成 null、Python 侧 `os.environ.get` 拿到 `'  '` 仍是真值，所以合成时要按 trim 后判空。
